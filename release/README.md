# Display Power Bridge

**显示器电源桥**：把 Windows 的显示器电源状态与显示器的 DDC/CI 电源控制连接起来。

本工具关注显示器的关闭、恢复和远程可用性，不负责亮度调节。它常驻任务栏，可配合 UU 等远程控制工具使用。

## 为何开发本工具

这个工具不是一开始就采用 DDC/CI，而是经过几条路线反复验证后留下的方案。

### 1. 尝试内核输入过滤驱动

最初的目标是：Windows 自动关闭屏幕后接管物理鼠标，只有检测到持续、足够可靠的真实移动才恢复显示，同时保留键盘唤醒和 UU 远程控制。

为阻止轻微鼠标移动直接唤醒，曾转向内核输入过滤驱动：安装 WDK、生成驱动、信任测试证书、安装 INF，并实际测试了服务和卸载流程。结果遇到几个现实问题：

- 测试证书只能解决开发机上的信任，不能作为适合日常使用的正式内核驱动签名方案；
- 驱动安装后曾出现光标被定住、鼠标异常、类似 USB 设备重新插入的提示音；
- 卸载服务后输入栈状态没有立即恢复，必须重启才能让鼠标恢复正常；
- 驱动一旦发生异常，影响的是整个系统的输入设备，而不是单个应用。

这条路线的系统级风险和签名成本都太高，因此没有继续作为日常工具的基础。

### 2. 研究 EasyScreenOff 的输入锁定思路

随后参考 EasyScreenOff：保留 Windows 的输入阻断效果，尝试在输入被阻断时寻找仍可观察的物理鼠标信号，再以连续移动次数、移动幅度和间隔判断是否真的要恢复显示。

期间尝试过 Raw Input、HID collection 读取、`BlockInput` 下的光标采样和独立采样工具。实际结果无法形成稳定条件：

- 有时轻微移动就立即唤醒；
- 有时无论移动多久、幅度多大都没有有效信号；
- Raw Input 的回调结构和不同鼠标设备存在兼容问题；
- HID 设备常被 Windows 独占，用户态读取返回拒绝访问；
- `BlockInput` 下能观察到的信号不足以可靠区分真实物理移动和系统状态变化；
- 多次试验还出现过回调异常、崩溃退出和恢复状态不一致。

这说明“先完全锁住输入，再从用户态猜测物理移动”本身就缺少稳定的数据来源。继续堆叠阈值，只会在“轻轻一动就亮”和“怎么动都不亮”之间来回回归，所以放弃了这条路线。

### 3. 转向 DDC/CI 显示器电源控制

最终把问题拆成两个更明确的部分：

1. Windows 的自动关屏由 Windows 自己处理；
2. 显示器的实际电源状态由显示器支持的 DDC/CI `VCP 0xD6` 控制，并由本工具在 Windows 广播和恢复条件满足时补发信号。

这样不再拦截系统输入，也不需要内核驱动。首次运行会让用户连接好远程控制，交互式测试 `0xD6` 的关屏值，并用回车或弹窗确认成功、用 Esc 或弹窗确认失败。只有测试成功且恢复成功，显示器配置才会保存。

当前方案还会监听 Windows 的显示电源广播，在自动关屏事件到达后尽快补发 DDC/CI；恢复时可等待显示链路稳定，再发送 `0x01`。退出、异常和系统注销/关机也会尝试连续发送三次 `0x01`，尽量避免显示器停留在不可恢复状态。

这条路线仍然受显示器固件、转接器、线材和 DDC/CI 实现影响，所以工具保留了首次交互测试、滚动日志、恢复重试和失败后的人工确认。

## 首次运行

双击 `run_display_power_bridge.bat`：

1. 选择要测试的物理显示器；
2. 先连接 UU 或其他远程控制工具；
3. 选择 `VCP 0xD6` 值。界面会显示每个值的含义：
   - `0x01`：开机 / 正常显示；
   - `0x02`：待机；
   - `0x03`：挂起；
   - `0x04`：关闭显示输出；
   - `0x05`：类似电源键的单向命令，风险较高；
4. 点击交互式测试；默认值是此前测试使用的 `0x04`；
5. 在远程端观察显示器。显示器正常关闭、远程连接仍可操作时选择成功；黑屏、无法恢复或远程断开时选择失败；
6. 工具会发送 `VCP 0xD6 = 0x01` 尝试恢复显示器。只有确认成功并且恢复命令成功，配置才会保存。

## 唤醒条件

托盘触发的关屏可以选择：

- 连续达到 N 次有效鼠标移动后恢复显示，默认 10 次；
- 键盘任意键恢复显示；
- 设置最小移动像素、允许的移动间隔和有效移动次数；
- 设置自动关屏恢复前等待显示链路稳定的时间；
- 设置托盘左键单击或双击行为，以及显示窗口或关闭屏幕。

鼠标判断只用于恢复条件，不会安装鼠标过滤驱动，也不会改变系统输入栈。

## Windows 电源计划和睡眠

工具注册 `GUID_CONSOLE_DISPLAY_STATE` 和 `GUID_MONITOR_POWER_ON` 两类 Windows 显示电源广播，每类注册最多重试三次，注册结果会写入滚动日志。

Windows 自动关屏广播到达后，工具会在独立线程中尽快发送配置的 `VCP 0xD6` 关屏命令，同时启动可选的鼠标和键盘恢复监听。恢复条件满足后，自动关屏模式会等待配置的显示链路稳定时间，再发送 `VCP 0xD6 = 0x01`。进入睡眠会停止恢复监听，从睡眠恢复后重新等待下一次关屏广播。

广播已经由 Windows 在显示电源切换过程中发出，因此补发时机仍受 Windows 和显示链路控制；独立发送线程用于去掉原先的界面轮询等待，尽量赶在显示器进入无信号前发送。

## 安全和故障恢复

- `0x05` 是高风险的单向命令，除非已经完成远程可恢复性测试，否则不要使用；
- 显示器配置依赖固件、接口、转接器和线材，首次测试必须保留远程控制通道；
- 正常退出、程序异常、控制台终止、注销或关机时，工具会独立尝试发送三次 `VCP 0xD6 = 0x01`；一次失败或异常不会跳过后续尝试；
- 退出、测试超时和启动错误都会按失败处理，并尝试恢复显示器；
- 同一时间只允许一个实例运行。

## 开机自启动

主窗口提供“登录 Windows 后自动启动（当前用户）”复选框。启用后，工具会写入当前用户的注册表启动项：HKCU\\Software\\Microsoft\\Windows\\CurrentVersion\\Run，无需管理员权限。登录桌面后程序会以托盘模式启动；首次尚未完成 DDC/CI 测试时仍会显示引导窗口。

这里使用注册表启动项是因为本工具是当前用户的托盘 GUI，不需要服务权限，也不需要计划任务的后台会话切换。关闭复选框会立即删除该启动项。若移动了 EXE 文件，建议先关闭自启动，再在新位置重新启用，使启动项更新为新路径。

## 后续运行

工具会常驻任务栏通知区域。托盘菜单提供重新测试、关闭屏幕、恢复屏幕和退出。配置保存在 `%APPDATA%\\DisplayPowerBridge\\config.json`；旧位置 `%APPDATA%\\DdcCiScreenGuard\\config.json` 会作为兼容回退读取。

主程序是 `display_power_bridge.py`，启动脚本是 `run_display_power_bridge.bat`。

## 构建原生二进制文件

双击 `build_display_power_bridge.bat`，或在 PowerShell 中执行：

```powershell
.\\build_display_power_bridge.ps1
```

构建流程会自动：

1. 选择能正常加载 PyInstaller 的 Python；
2. 安装缺失的 PyInstaller；
3. 找到 PATH、`UPX_PATH` 或项目缓存中的 UPX；
4. 如果没有找到 UPX，从 UPX 官方 GitHub 发布页下载 Windows 版本并缓存到 `.build\\upx`；下载优先使用 `curl.exe`，带重试、断点续传和速度停滞检测，失败后再尝试 BITS 或 PowerShell；
5. 使用 PyInstaller 生成单文件、无控制台窗口的 Windows 原生 EXE，并在归档内部压缩 Python/Tk 相关 DLL；
6. 同时生成内部 `--noupx` 结果用于体积比较，但发布目录只保留压缩版，并检查发布文件非空。

PyInstaller 单文件包含 Python 运行时和 Tk/Tcl。直接对最终归档做 UPX 压缩通常几乎没有效果，而且对已经含有 UPX 内部文件的单文件再次压缩可能导致启动失败。因此流程把 UPX 路径传给 PyInstaller，让内部 DLL 在归档前压缩；发布版不再二次压缩。构建会排除本工具不使用的 SSL、Hash、BZ2、LZMA、Decimal、Zstandard、网络协议、序列化和调试标准库，并通过自定义 Tk hook 移除 Tcl 时区数据库、可选包、未使用的图片、文件对话框辅助脚本和多余语言消息。两个简单数据类使用轻量普通类实现，避免引入额外的反射依赖。

输出位于 `release`：

- `DisplayPowerBridge.exe`：UPX 压缩后的发布文件；
- `build-metadata.json`：记录 Python、PyInstaller、UPX、构建时间、压缩前后体积和 SHA-256；
- `README.md`：随发布文件复制的说明。

如果不希望自动下载 UPX，可执行：

```powershell
.\\build_display_power_bridge.ps1 -UpxPath C:\\Tools\\upx\\upx.exe -NoDownloadUpx
```

构建脚本统一要求 Python 3.14.3，不会回落到其他 Python 版本。若机器上安装了多个版本，请使用 `-Python` 指向 3.14.3 的解释器。
